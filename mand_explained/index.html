Cub3D: Inside the Raycaster
01

The Big Picture

What ./cub3D actually does between the moment you launch it and the moment a 3D corridor appears — the program lifecycle and the frame pipeline.

A 3D world from a 2D text file

Cub3D is a raycasting engine. The world is just a grid of characters — 1 is a wall, 0 is floor — and yet the player walks through it in first person. The whole trick: 1280 rays per frame, one per screen column, each answering a single question: "how far is the nearest wall in this direction?"

🎯
Evaluator question #1 (it always comes first)

"Walk me through your program from main() to the first frame." This module is exactly that answer. If you can narrate the two diagrams below from memory, you've passed the opening question.

📜
Parser — src/parsing/

Reads the .cub file once at startup. Either produces a fully validated map + config, or prints Error\n and exits. Nothing invalid survives past this point.

🧭
Player state — t_player

Five doubles, no angles: position (pos_x, pos_y), direction vector (dir), camera plane vector (plane). The entire camera model.

📡
Raycaster — src/execution/

For each screen column: build a ray, run DDA until it hits a 1, report distance and which wall face was hit.

🖼️
Renderer — src/render/

Turns each ray result into one vertical stripe: ceiling color on top, textured wall slice in the middle, floor color below. Writes pixels into an off-screen image.

⌨️
Events — src/events/

MLX hooks that record which keys are held, and per-frame functions that turn held keys into movement and rotation.

Why parse before MLX?

Two reasons: a bad map must fail fast with only Error\n + message (no window flash), and error cleanup is much simpler when there are no graphics resources to undo yet. cub_init's zeroing is what makes exit_error → cub_destroy safe at any point: every destroy is guarded by if (ptr).

02

Parsing & Validation

Half the evaluation lives here. The evaluator will feed your program broken maps and expect a clean Error\n every single time.

Anatomy of a .cub file

Six configuration elements (any order, any number of blank lines between them), then the map — which must come last.

NO ./path.xpm North wall texture — stored in tex_path[TEX_NO] (index 0)
SO / WE / EA South, West, East textures — indices 1, 2, 3
F 220,100,0 Floor color: three comma-separated ints, each 0–255
C 225,30,0 Ceiling color, same rules
1 0 N space Map rows: walls, floor, exactly one spawn (N/S/E/W), spaces = void outside the playable area

Each parsed element flips one bit in parsed_flags — a bitmask. Duplicate identifier? The bit is already set → error. Map starts but parsed_flags != 63? "Map found before all elements" → error.

One line comes in — who handles it?

parse_file() reads line by line with get_next_line and dispatches. Watch the parsing crew handle a file:

The map grid: jagged on purpose

Rows are stored as-is (newline trimmed, tabs → spaces). Rows can have different lengths — the code never pads them. That's why every place that indexes the grid first checks x < ft_strlen(grid[y]): the DDA loop, collision, and validation all do this.

src/parsing/validate_map.c 

if (ny < 0 || ny >= cub->map.height)
    exit_error(cub, "Map is not enclosed by walls");
row_len = ft_strlen(cub->map.grid[ny]);
if (nx < 0 || nx >= row_len)
    exit_error(cub, "Map is not enclosed by walls");
if (cub->map.grid[ny][nx] == ' ')
    exit_error(cub, "Map is not enclosed by walls");
PLAIN ENGLISH

A neighbor above the first row or below the last row means a walkable cell touches the void → not enclosed.

Rows are jagged, so measure this row's actual length.

A neighbor past the end of a short row is also the void → same error.

And a literal space inside the map counts as void too. Walkable cell touching space = leak in the walls.

💡
Why 8 neighbors instead of flood fill?

Both prove enclosure. The invariant here: every walkable cell (0 or spawn) must be fully surrounded by non-void cells — including diagonals. If a walkable cell can "see" void in any of 8 directions, the map leaks. It's a local check, O(8) per cell, no recursion, no visited array — simpler to defend at evaluation than flood fill, and it catches diagonal gaps that 4-neighbor checks miss.

The error contract

Every failure path goes through one function. No exceptions, no leaks.

1
Print Error\n + message to stderr

Exactly the subject format: ft_putstr_fd("Error\n", 2) then the specific reason.

2
cub_destroy() — free everything that exists

Textures, image, window, display, grid rows, texture paths. Every free is guarded, and cub_init's zeroing guarantees the guards are meaningful even on the earliest error.

3
exit(1)

Non-zero status. The evaluator will run your program under valgrind on a broken map — this path must be leak-free too.

⚠️
Known leak window — be ready for this question

When exit_error fires mid-parsing, the current get_next_line line and GNL's internal stash can still be allocated. post_map_check() shows the careful pattern: it frees the line and closes the fd before calling exit_error. If valgrind shows a few "still reachable" bytes from GNL on error paths, know exactly where they come from and why.

03

The Camera Without Angles

No angle variable anywhere in the code — the camera is two vectors. This is the single most important idea to defend at the table.

Three things define the view

The whole camera is five doubles in t_player: a position, a direction vector dir (unit length), and a camera plane vector plane (length 0.66, always perpendicular to dir).

The segment from dir + plane·(−1) to dir + plane·(+1) is your screen, laid flat inside the 2D world. Casting a ray through screen column x means aiming at the matching point on that segment.

Why 0.66? The FOV math

Half the screen spans from the tip of dir to the tip of plane. Those two are perpendicular, so the half-angle of the FOV satisfies a right-triangle relation:

tan(FOV / 2) = |plane| / |dir| = 0.66 / 1
FOV = 2 · atan(0.66) ≈ 66.8°

Want a 90° FOV? Set |plane| = 1.0 (tan 45° = 1). The ratio of the two vector lengths is the FOV — nothing else in the code needs to change.

💡
Raycasting is not ray tracing — say it before they ask

Ray tracing shoots a ray per pixel in 3D and simulates light bounces. Ray casting here shoots one ray per column through a flat 2D grid and only finds the first wall. Cost: O(columns × cells crossed), real-time on 1992 hardware. The subject says "ray-casting" — using the right word at the table matters.

From column number to ray direction

src/execution/ray_utils.c — init_ray 

camera_x = 2.0 * x / WIN_W - 1.0;
ray->dir_x = p->dir_x + p->plane_x * camera_x;
ray->dir_y = p->dir_y + p->plane_y * camera_x;
ray->map_x = (int)p->pos_x;
ray->map_y = (int)p->pos_y;
PLAIN ENGLISH

Remap column x ∈ [0, 1280) onto [−1, +1): left edge → −1, center → 0, right edge → just under +1.

The ray direction is the look direction, nudged sideways along the camera plane by camera_x. At the center the ray is dir; at the edges it's dir ± plane.

Same formula for y. Note: the resulting ray is NOT normalized — and that's fine (module 4 explains why it never needs to be).

Start the grid walk in the cell containing the player — just truncate the position to ints.

One subtlety worth volunteering at the eval: equal steps in camera_x (not equal angles) is what makes straight walls render straight. An angle-based camera that sweeps the FOV in equal angular steps produces curved walls — that's the fisheye family of bugs before fisheye is even discussed.

Spawning: how N/S/E/W become vectors

init_player() centers the player in the cell (x + 0.5, y + 0.5) and sets the two vectors. Remember the map's coordinate system: y grows downward (row 0 is the top line of the file), so North is dir = (0, −1).

N

dir (0, −1)

plane (0.66, 0) — points to the player's left-to-right axis, east.

S

dir (0, 1)

plane (−0.66, 0) — sign flips so "screen right" stays on the player's right.

E

dir (1, 0)

plane (0, 0.66) — perpendicular, consistent handedness.

W

dir (−1, 0)

plane (0, −0.66) — flip the dir, flip the plane.

The rule behind all four: plane = 0.66 · (−dir_y, dir_x). Get one sign wrong and the world renders mirrored — left arrow turns the view right. That's the classic symptom evaluators know to look for.

04

DDA: Walking the Grid

Given a ray, find the first wall it hits — exactly, in a handful of additions per cell. This is the algorithm the project is named for.

Why not just step in tiny increments?

The naive approach — advance the ray by 0.01 and check the cell each time — has two fatal flaws, and naming them is a great eval answer:

🕳️

It can miss

A fixed step can jump clean over a wall corner or land just past a thin boundary. Any step size is either wrong somewhere or absurdly slow.

🐢

It's slow

Hundreds of samples per ray × 1280 rays × 60 fps. DDA does it in one operation per cell crossed — typically 5–20 per ray.

📐

DDA is exact

A ray only ever enters a new cell by crossing a vertical or horizontal grid line. So only check those crossings — every cell on the path, none skipped.

The DDA insight: the ray's crossings with vertical lines are evenly spaced along the ray, and so are its crossings with horizontal lines. Precompute the two spacings, then race them against each other.

delta_dist — the only real derivation

How far do you travel along the ray to move exactly 1 unit in x? Pythagoras on the triangle with legs 1 and dir_y/dir_x:

deltaDistX = √(1 + dir_y²/dir_x²) = |rayDir| / |dir_x|
deltaDistY = √(1 + dir_x²/dir_y²) = |rayDir| / |dir_y|
// divide both by |rayDir| — every distance scales uniformly:
deltaDistX = |1 / dir_x|    deltaDistY = |1 / dir_y|

Dividing all distances by |rayDir| is legal because DDA only ever compares side_dists and the renderer only needs distance in consistent units. The payoff is huge: the code never normalizes the ray, and the distance that falls out at the end is already the perpendicular distance the projection wants (module 5 proves it).

💡
Defend this exact line: delta_x = fabs(1.0 / ray->dir_x)

"Distance along the ray per unit of x, expressed in units of the ray's own length." If dir_x == 0 the ray is perfectly vertical and never crosses a vertical line — the code stores 1e30 so the X side always loses the comparison, without ever producing inf or dividing by zero.

side_dist — getting to the first grid line

delta is the spacing between crossings; side_dist is the head start: distance from the player to the first crossing on each axis. It depends on where the player stands inside the cell, and on the ray's sign:

src/execution/ray_utils.c — init_step_side 

if (ray->dir_x < 0)
{
    ray->step_x = -1;
    ray->side_dist_x = (p->pos_x - ray->map_x) * ray->delta_x;
}
else
{
    ray->step_x = 1;
    ray->side_dist_x = (ray->map_x + 1.0 - p->pos_x) * ray->delta_x;
}
PLAIN ENGLISH

Ray points left (−x): the next vertical line is the cell's LEFT edge.

So each DDA step on this axis will decrement map_x.

The fraction of a cell between the player and that left edge is (pos_x − map_x); multiply by delta_x to convert "cells of x" into "distance along the ray".

Ray points right (+x): the next vertical line is the RIGHT edge.

Steps will increment map_x.

Distance to the right edge is (map_x + 1 − pos_x) cells of x — note the +1.0, the single most bug-prone constant in the whole raycaster.

The loop: two runners racing

Picture two runners on the same ray: one stops at every vertical grid line, one at every horizontal line. At each iteration, whoever is behind takes their next stride. Whichever runner moves, that axis was crossed — and that's recorded as side.

src/execution/raycaster.c — run_dda 

if (ray->side_dist_x < ray->side_dist_y)
{
    ray->side_dist_x += ray->delta_x;
    ray->map_x += ray->step_x;
    ray->side = 0;
}
else
{
    ray->side_dist_y += ray->delta_y;
    ray->map_y += ray->step_y;
    ray->side = 1;
}
PLAIN ENGLISH

The next vertical-line crossing is closer than the next horizontal one…

…so take that crossing: schedule the one after it (add the constant spacing delta_x)…

…and enter the neighboring cell on the x axis.

side = 0 remembers "I entered through a vertical line" → I'm looking at an East/West-facing wall.

Otherwise the horizontal crossing comes first — same logic on y.

side = 1 → entered through a horizontal line → North/South-facing wall. After moving, the loop checks bounds and whether grid[map_y][map_x] == '1'.

Loop exit conditions, in order: the new cell is out of bounds (jagged rows make the per-row ft_strlen check necessary), or the cell is a wall. side keeps the value from the last step — the axis through which the wall was entered. That single int later picks the texture and the fisheye formula.

Spot the bug

This is a deliberately broken version of init_step_side's positive branch — the kind of bug that makes walls wobble as you strafe. Click the broken line.

1 if (ray->dir_x < 0)
2 {
3 ray->step_x = -1;
4 ray->side_dist_x = (p->pos_x - ray->map_x) * ray->delta_x;
5 }
6 else
7 {
8 ray->step_x = 1;
9 ray->side_dist_x = (ray->map_x - p->pos_x) * ray->delta_x;
10 }
🔍
Why it matters

The real code uses (map_x + 1.0 - pos_x): the distance to the cell's right edge. The buggy version computes map_x − pos_x, which is ≤ 0 — a negative head start. The first comparison then always favors x, walls shift by up to a cell, and the error changes as the player moves inside the cell: walls "swim". If an evaluator asks "what's the +1.0 for?", this is the answer.

05

Projection, Fisheye & Textures

The ray hit a wall. Now: how tall is the stripe, why isn't it curved, and which texture pixels fill it?

Fisheye: the bug you fix by never creating it

Use the straight-line (Euclidean) distance to the wall and a flat wall renders as a barrel: edge rays are longer than the center ray even when the wall is straight ahead, so edge columns draw shorter. The cure: measure distance perpendicular to the camera plane — how far the wall is "in front of" you, ignoring the sideways component.

The elegant part of this implementation: the perpendicular distance is never computed from the Euclidean one. It falls straight out of the DDA bookkeeping:

// hit = pos + t·rayDir. The scaled side_dists measure exactly t,
// because crossing 1 unit of x costs Δt = 1/|dir_x| (our delta).
// The loop overshoots by one step, so undo it:
t = side_dist − delta  (for the axis that was hit)

// perpendicular distance = (hit − pos) projected onto unit dir:
perpDist = t·rayDir · dir = t·(dir + plane·camera_x) · dir
         = t·(|dir|² + camera_x·(plane·dir)) = t·(1 + 0) = t

Because |dir| = 1 and plane ⊥ dir, the projection collapses to t itself. So perp_dist = side_dist − delta — one subtraction, fisheye-free by construction. This derivation is the strongest answer in the entire evaluation.

From distance to a stripe on screen

src/execution/ray_utils.c — calc_draw_params 

if (ray->side == 0)
    ray->perp_dist = ray->side_dist_x - ray->delta_x;
else
    ray->perp_dist = ray->side_dist_y - ray->delta_y;
if (ray->perp_dist < 0.001)
    ray->perp_dist = 0.001;
dw->height = (int)(WIN_H / ray->perp_dist);
dw->start = horizon - dw->height / 2;
PLAIN ENGLISH

Hit through a vertical line? Then the x-runner's bookkeeping holds the answer…

…subtract one delta to undo the loop's final overshoot. That IS the perpendicular distance.

Same on the y side for horizontal hits.

Clamp near-zero distance — standing flush against a wall must not divide by ~0.

Similar triangles: a 1-unit-tall wall at distance d projects to WIN_H/d pixels. At d = 1 the wall exactly fills the 720px screen.

Center the stripe on the horizon (WIN_H/2 in the mandatory spec) — equal wall above and below eye level. start/end are then clamped to the screen.

💡
Why height = WIN_H / perp_dist?

Walls are 1 unit tall and the projection plane sits at distance 1 (the dir length). Similar triangles: projected size / screen scale = real size / distance ⇒ pixels = WIN_H · (1 / perp_dist). Double the distance, half the stripe. Linear, no trig.

Which texture, and which column of it?

Two decisions. Which texture: side + step sign. Hit a vertical line while stepping left (step_x < 0)? You're looking at the block's east-facing side from the west → WE. The other three follow the same logic. Which column of the texture: where along the wall's face the hit landed:

src/render/draw_wall.c — calc_wall_x / calc_tex_x 

if (ray->side == 0)
    wall_x = p->pos_y + ray->perp_dist * ray->dir_y;
else
    wall_x = p->pos_x + ray->perp_dist * ray->dir_x;
wall_x -= floor(wall_x);
tex_x = (int)(wall_x * tex->width);
if (ray->side == 0 && ray->dir_x > 0)
    tex_x = (tex->width - 1) - tex_x;
PLAIN ENGLISH

Hit a vertical wall face? The hit's x is a known grid line — the interesting coordinate is y.

Reconstruct it: pos + t·rayDir, using perp_dist as t (the same t from the projection proof — one more payoff of the scaled units).

Horizontal face: symmetric, take the x coordinate.

Keep only the fractional part: 0.0 = one edge of this wall block, 1.0 = the other. That's the horizontal position ON the wall face.

Scale [0,1) into texture pixel columns.

Mirror correction: depending on which side you view the face from, "left along the wall" flips. Without this, opposing faces render mirror-imaged — text on walls reads backwards.

Painting the column: texture stepping

The stripe is height pixels tall but the texture is 64. One texel per screen pixel, walked with a fixed-point style accumulator — no division per pixel:

src/render/draw_wall.c — draw_wall_stripe 

dw.step = (double)tex->height / dw.height;
dw.pos = (dw.start - cub->horizon + dw.height / 2) * dw.step;
draw_ceiling(cub, x, dw.start);
draw_tex_col(cub, x, &dw, tex);
draw_floor(cub, x, dw.end + 1);
PLAIN ENGLISH

How many texture rows per screen row. Far wall: stripe is short, step > 1, texture is skimmed. Close wall: step < 1, texels repeat.

The anchor trick: if the wall is taller than the screen, start was clamped to 0 — so we must begin sampling partway INTO the texture, not at row 0. This computes exactly how far in. Unclamped stripes give 0 here.

Solid ceiling color from the top of the screen down to the stripe.

Then the textured wall: each row reads texel (tex_x, (int)pos), advances pos by step.

Then solid floor color down to the bottom. Three bands = the entire column drawn, every pixel exactly once.

One byte-level detail to own: put_px computes data + y·line_len + x·(bpp/8) and writes through an unsigned int * cast. line_len is the padded bytes-per-row MLX reports — using WIN_W·4 instead is the classic skewed-image bug. And writing without the cast would store a single byte instead of 4 (blue-only screen).

Movement, Rotation & the Evaluation

The last moving parts — then a mock evaluation covering the traps evaluators actually set.

Rotation: one matrix, two vectors

Turning left/right rotates both dir and plane by the same angle with the standard 2D rotation matrix. Rotate only dir and the perpendicularity breaks — the view shears and the FOV drifts every turn.

src/events/rotation.c — rotate_vectors 

cos_a = cos(angle);
sin_a = sin(angle);
old_dir_x = p->dir_x;
p->dir_x = old_dir_x * cos_a - p->dir_y * sin_a;
p->dir_y = old_dir_x * sin_a + p->dir_y * cos_a;
PLAIN ENGLISH

Compute sin/cos once — angle is ±ROT_SPD (0.03 rad ≈ 1.7° per frame).

Save dir_x BEFORE overwriting it — the second line needs the OLD x. Forgetting this is the classic rotation bug: the view spirals inward and the vectors shrink.

Matrix row 1: x' = x·cos − y·sin.

Matrix row 2: y' = x·sin + y·cos. Lengths preserved exactly, so |dir| stays 1 and |plane| stays 0.66 forever — the FOV never drifts.

⚠️
Heads-up: the comment above this function has a typo

The doc comment in rotation.c writes the second row as new_y = old_y * sin(a) + old_y * cos(a) — it should be old_x * sin(a) + old_y * cos(a). The code is correct; the comment isn't. An evaluator reading comments aloud might catch it — better you say it first (or fix it before the defense).

Movement: vectors again, plus sliding collision

W/S move along ±dir; A/D strafe along ±plane — no extra math needed, the perpendicular vector already exists. The polish is in how collisions are tested:

src/events/movement.c — move_along 

nx = cub->player.pos_x + sign * vx * MOVE_SPD;
ny = cub->player.pos_y + sign * vy * MOVE_SPD;
if (can_move(&cub->map, nx, cub->player.pos_y))
    cub->player.pos_x = nx;
if (can_move(&cub->map, cub->player.pos_x, ny))
    cub->player.pos_y = ny;
PLAIN ENGLISH

Candidate position: current + direction vector scaled by speed (0.05 cells per frame).

Test the x move ALONE, keeping y fixed. Legal? Apply just the x part.

Then test the y move alone. The two axes are independent—

—which is what makes you SLIDE along a wall you walk into diagonally, instead of sticking to it. One blocked axis doesn't veto the other.

can_move() itself doesn't test a point — it tests a 0.2-radius bounding box: all four corners of a small square around the candidate position must land in non-wall cells. That keeps an air gap from walls (no texture z-fighting against your face) and stops corner-clipping diagonally between two walls.

Lifecycle, memory, and what counts as "extra"

1
Two exit doors, one cleanup

ESC and the window's ✕ both land in close_hook → mlx_loop_end → cub_destroy → exit(0). Error paths take exit_error → same cub_destroy → exit(1). One free-everything function, called from every door.

2
Destroy order matters

cub_destroy: textures → screen image → window → display → grid → texture path strings. MLX resources before mlx_destroy_display, and every step guarded so the function is safe whether you crashed during parsing or after an hour of play.

3
Know your mandatory vs. polish

Distance fog (FOG_K), darker N/S faces (SIDE_SHADE), floor/ceiling gradients, head-bob (horizon, bob_t) and the crosshair are extras layered onto the mandatory part. Be ready to point at them, say "this is polish, here's the line where the mandatory behavior would be WIN_H / 2 and a flat color", and explain them anyway.
