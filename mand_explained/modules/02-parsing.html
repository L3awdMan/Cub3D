Parsing & Validation

Half the evaluation lives here. The evaluator will feed your program broken maps and expect a clean Error\n every single time.

Anatomy of a .cub file

Six configuration elements (any order, any number of blank lines between them), then the map — which must come last.

NO ./path.xpm North wall texture — stored in tex_path[TEX_NO] (index 0)
SO / WE / EA South, West, East textures — indices 1, 2, 3
F 220,100,0 Floor color: three comma-separated ints, each 0–255
C 225,30,0 Ceiling color, same rules
1 0 N space Map rows: walls, floor, exactly one spawn (N/S/E/W), spaces = void outside the playable area

Each parsed element flips one bit in parsed_flags — a bitmask. Duplicate identifier? The bit is already set → error. Map starts but parsed_flags != 63? "Map found before all elements" → error.

One line comes in — who handles it?

The map grid: jagged on purpose

Rows are stored as-is (newline trimmed, tabs → spaces). Rows can have different lengths — the code never pads them. That's why every place that indexes the grid first checks x < ft_strlen(grid[y]): the DDA loop, collision, and validation all do this.

src/parsing/validate_map.c 

if (ny < 0 || ny >= cub->map.height)
    exit_error(cub, "Map is not enclosed by walls");
row_len = ft_strlen(cub->map.grid[ny]);
if (nx < 0 || nx >= row_len)
    exit_error(cub, "Map is not enclosed by walls");
if (cub->map.grid[ny][nx] == ' ')
    exit_error(cub, "Map is not enclosed by walls");
PLAIN ENGLISH

A neighbor above the first row or below the last row means a walkable cell touches the void → not enclosed.

Rows are jagged, so measure this row's actual length.

A neighbor past the end of a short row is also the void → same error.

And a literal space inside the map counts as void too. Walkable cell touching space = leak in the walls.

💡
Why 8 neighbors instead of flood fill?

Both prove enclosure. The invariant here: every walkable cell (0 or spawn) must be fully surrounded by non-void cells — including diagonals. If a walkable cell can "see" void in any of 8 directions, the map leaks. It's a local check, O(8) per cell, no recursion, no visited array — simpler to defend at evaluation than flood fill, and it catches diagonal gaps that 4-neighbor checks miss.

The error contract

Every failure path goes through one function. No exceptions, no leaks.

1
Print Error\n + message to stderr

Exactly the subject format: ft_putstr_fd("Error\n", 2) then the specific reason.

2
cub_destroy() — free everything that exists

Textures, image, window, display, grid rows, texture paths. Every free is guarded, and cub_init's zeroing guarantees the guards are meaningful even on the earliest error.

3
exit(1)

Non-zero status. The evaluator will run your program under valgrind on a broken map — this path must be leak-free too.

⚠️
Known leak window — be ready for this question

When exit_error fires mid-parsing, the current get_next_line line and GNL's internal stash can still be allocated. post_map_check() shows the careful pattern: it frees the line and closes the fd before calling exit_error. If valgrind shows a few "still reachable" bytes from GNL on error paths, know exactly where they come from and why.
