Rotation: one matrix, two vectors

Turning left/right rotates both dir and plane by the same angle with the standard 2D rotation matrix. Rotate only dir and the perpendicularity breaks — the view shears and the FOV drifts every turn.

src/events/rotation.c — rotate_vectors 

cos_a = cos(angle);
sin_a = sin(angle);
old_dir_x = p->dir_x;
p->dir_x = old_dir_x * cos_a - p->dir_y * sin_a;
p->dir_y = old_dir_x * sin_a + p->dir_y * cos_a;
PLAIN ENGLISH

Compute sin/cos once — angle is ±ROT_SPD (0.03 rad ≈ 1.7° per frame).

Save dir_x BEFORE overwriting it — the second line needs the OLD x. Forgetting this is the classic rotation bug: the view spirals inward and the vectors shrink.

Matrix row 1: x' = x·cos − y·sin.

Matrix row 2: y' = x·sin + y·cos. Lengths preserved exactly, so |dir| stays 1 and |plane| stays 0.66 forever — the FOV never drifts.

⚠️
Heads-up: the comment above this function has a typo

The doc comment in rotation.c writes the second row as new_y = old_y * sin(a) + old_y * cos(a) — it should be old_x * sin(a) + old_y * cos(a). The code is correct; the comment isn't. An evaluator reading comments aloud might catch it — better you say it first (or fix it before the defense).

Movement: vectors again, plus sliding collision

W/S move along ±dir; A/D strafe along ±plane — no extra math needed, the perpendicular vector already exists. The polish is in how collisions are tested:

src/events/movement.c — move_along 

nx = cub->player.pos_x + sign * vx * MOVE_SPD;
ny = cub->player.pos_y + sign * vy * MOVE_SPD;
if (can_move(&cub->map, nx, cub->player.pos_y))
    cub->player.pos_x = nx;
if (can_move(&cub->map, cub->player.pos_x, ny))
    cub->player.pos_y = ny;
PLAIN ENGLISH

Candidate position: current + direction vector scaled by speed (0.05 cells per frame).

Test the x move ALONE, keeping y fixed. Legal? Apply just the x part.

Then test the y move alone. The two axes are independent—

—which is what makes you SLIDE along a wall you walk into diagonally, instead of sticking to it. One blocked axis doesn't veto the other.

can_move() itself doesn't test a point — it tests a 0.2-radius bounding box: all four corners of a small square around the candidate position must land in non-wall cells. That keeps an air gap from walls (no texture z-fighting against your face) and stops corner-clipping diagonally between two walls.

Lifecycle, memory, and what counts as "extra"

1
Two exit doors, one cleanup

ESC and the window's ✕ both land in close_hook → mlx_loop_end → cub_destroy → exit(0). Error paths take exit_error → same cub_destroy → exit(1). One free-everything function, called from every door.

2
Destroy order matters

cub_destroy: textures → screen image → window → display → grid → texture path strings. MLX resources before mlx_destroy_display, and every step guarded so the function is safe whether you crashed during parsing or after an hour of play.

3
Know your mandatory vs. polish

Distance fog (FOG_K), darker N/S faces (SIDE_SHADE), floor/ceiling gradients, head-bob (horizon, bob_t) and the crosshair are extras layered onto the mandatory part. Be ready to point at them, say "this is polish, here's the line where the mandatory behavior would be WIN_H / 2 and a flat color", and explain them anyway.
