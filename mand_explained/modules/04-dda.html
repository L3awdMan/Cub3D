DDA: Walking the Grid

Given a ray, find the first wall it hits — exactly, in a handful of additions per cell. This is the algorithm the project is named for.

Why not just step in tiny increments?

The naive approach — advance the ray by 0.01 and check the cell each time — has two fatal flaws, and naming them is a great eval answer:

🕳️

It can miss

A fixed step can jump clean over a wall corner or land just past a thin boundary. Any step size is either wrong somewhere or absurdly slow.

🐢

It's slow

Hundreds of samples per ray × 1280 rays × 60 fps. DDA does it in one operation per cell crossed — typically 5–20 per ray.

📐

DDA is exact

A ray only ever enters a new cell by crossing a vertical or horizontal grid line. So only check those crossings — every cell on the path, none skipped.

The DDA insight: the ray's crossings with vertical lines are evenly spaced along the ray, and so are its crossings with horizontal lines. Precompute the two spacings, then race them against each other.

delta_dist — the only real derivation

How far do you travel along the ray to move exactly 1 unit in x? Pythagoras on the triangle with legs 1 and dir_y/dir_x:

deltaDistX = √(1 + dir_y²/dir_x²) = |rayDir| / |dir_x|
deltaDistY = √(1 + dir_x²/dir_y²) = |rayDir| / |dir_y|
// divide both by |rayDir| — every distance scales uniformly:
deltaDistX = |1 / dir_x|    deltaDistY = |1 / dir_y|

Dividing all distances by |rayDir| is legal because DDA only ever compares side_dists and the renderer only needs distance in consistent units. The payoff is huge: the code never normalizes the ray, and the distance that falls out at the end is already the perpendicular distance the projection wants (module 5 proves it).

💡
Defend this exact line: delta_x = fabs(1.0 / ray->dir_x)

"Distance along the ray per unit of x, expressed in units of the ray's own length." If dir_x == 0 the ray is perfectly vertical and never crosses a vertical line — the code stores 1e30 so the X side always loses the comparison, without ever producing inf or dividing by zero.

side_dist — getting to the first grid line

delta is the spacing between crossings; side_dist is the head start: distance from the player to the first crossing on each axis. It depends on where the player stands inside the cell, and on the ray's sign:

src/execution/ray_utils.c — init_step_side 

if (ray->dir_x < 0)
{
    ray->step_x = -1;
    ray->side_dist_x = (p->pos_x - ray->map_x) * ray->delta_x;
}
else
{
    ray->step_x = 1;
    ray->side_dist_x = (ray->map_x + 1.0 - p->pos_x) * ray->delta_x;
}
PLAIN ENGLISH

Ray points left (−x): the next vertical line is the cell's LEFT edge.

So each DDA step on this axis will decrement map_x.

The fraction of a cell between the player and that left edge is (pos_x − map_x); multiply by delta_x to convert "cells of x" into "distance along the ray".

Ray points right (+x): the next vertical line is the RIGHT edge.

Steps will increment map_x.

Distance to the right edge is (map_x + 1 − pos_x) cells of x — note the +1.0, the single most bug-prone constant in the whole raycaster.

The loop: two runners racing

Picture two runners on the same ray: one stops at every vertical grid line, one at every horizontal line. At each iteration, whoever is behind takes their next stride. Whichever runner moves, that axis was crossed — and that's recorded as side.

src/execution/raycaster.c — run_dda 

if (ray->side_dist_x < ray->side_dist_y)
{
    ray->side_dist_x += ray->delta_x;
    ray->map_x += ray->step_x;
    ray->side = 0;
}
else
{
    ray->side_dist_y += ray->delta_y;
    ray->map_y += ray->step_y;
    ray->side = 1;
}
PLAIN ENGLISH

The next vertical-line crossing is closer than the next horizontal one…

…so take that crossing: schedule the one after it (add the constant spacing delta_x)…

…and enter the neighboring cell on the x axis.

side = 0 remembers "I entered through a vertical line" → I'm looking at an East/West-facing wall.

Otherwise the horizontal crossing comes first — same logic on y.

side = 1 → entered through a horizontal line → North/South-facing wall. After moving, the loop checks bounds and whether grid[map_y][map_x] == '1'.

Loop exit conditions, in order: the new cell is out of bounds (jagged rows make the per-row ft_strlen check necessary), or the cell is a wall. side keeps the value from the last step — the axis through which the wall was entered. That single int later picks the texture and the fisheye formula.

Why it matters

The real code uses (map_x + 1.0 - pos_x): the distance to the cell's right edge. The buggy version computes map_x − pos_x, which is ≤ 0 — a negative head start. The first comparison then always favors x, walls shift by up to a cell, and the error changes as the player moves inside the cell: walls "swim". If an evaluator asks "what's the +1.0 for?", this is the answer.
