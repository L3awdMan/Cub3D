Module 13 · Game flow & cutscenes

One integer decides whether you're in a menu, playing, dead, winning, or watching a movie.

Everything you've seen so far — rays, sprites, combat, HUD — only happens during one state. The whole program is wrapped in a state machine built on a single field, cub->game_state. This module follows the player from the title screen, through a difficulty choice, into a floor, through death and respawn, and onward to the next floor via full-screen cutscenes.

The nine states

GS_PLAYING 0Normal gameplay — the only state that updates the world.
GS_DEAD 1You died; the "YOU ARE DEAD" overlay plays.
GS_WIN 2Floor cleared; "YOU WIN" overlay.
GS_CUTSCENE 3A full-screen movie is playing; world frozen.
GS_INTRO 4Title screen.
GS_MENU 5Main menu (Start / Settings / Difficulty).
GS_SETTINGS 6 · GS_DIFFICULTY 7Sub-screens.
GS_FADEOUT 8The clear→black transition that launches a run.

The front-end flow

menu_input() is the whole front-end, dispatched per key press by the current state. It reads like a flowchart.

1
Intro → Menu

Space/Enter on the title screen steps to GS_MENU.

2
Menu navigation

Up/Down (or W/S) move a wrapping cursor; Backspace goes back to intro. Confirm runs menu_select().

3
Select

Row 0 = Start (→ GS_FADEOUT), row 1 = GS_SETTINGS, row 2 = GS_DIFFICULTY.

4
Fade → cutscene → play

GS_FADEOUT auto-advances (no input): once the black frame is reached, the floor-1 intro cutscene plays, which ends in GS_PLAYING.

💡
Difficulty is the one menu choice that touches gameplay

Settings is cosmetic, but Difficulty writes cub->difficulty, and that feeds player_dmg(): ATTACK_DMG × {1.0, 1.5, 2.0} for Easy / Skilled / Gigachad. That's why the combat module kept calling player_dmg(cub) instead of the raw constant — this is the single dial that makes you take 6, 9, or 12 damage per hit.

Death & respawn

update_endgame() is the per-frame referee. In GS_PLAYING it watches hp; the instant it hits 0 it flips to GS_DEAD. Then it waits for a confirm key — but only after the death animation has fully played, so the Space you were holding to shoot can't skip the screen.

CODE — endgame_state_bonus.c:61 
void	update_endgame(t_cub *cub)
{
	if (cub->game_state == GS_PLAYING)
	{
		if (cub->player.hp <= 0)
			enter_state(cub, GS_DEAD);
	}
	else if (cub->game_state == GS_DEAD)
	{
		if (confirm_pressed(cub))
			respawn(cub);
	}
	else if (cub->game_state == GS_WIN)
	{
		if (cub->cutscene.final_done)
			return ;
		if (confirm_pressed(cub))
			advance_floor(cub);
	}
}
PLAIN ENGLISH

The per-frame state referee.

While playing...

...HP hit zero?

...switch to the death screen.

While on the death screen...

...confirm (after the anim) →

...restore the floor and play on.

While on the win screen...

...if this is the FINAL (floor-3) win, do nothing — stay here forever.

...otherwise confirm →

...advance to the next floor.

respawn() is why dying isn't game-over: it restores the floor to a snapshot taken when the floor loaded. capture_spawn() saved the player camera and the initial sprite array; respawn copies them back, refills HP, reseeds the lives counter, clears every projectile, flash and held key, and drops you back into GS_PLAYING.

⚡
The spawn snapshot is a deep-ish copy

capture_spawn doesn't just remember your position — it memcpys the entire sprite array into spawn_sprites. So respawn brings back every enemy you killed, in their original positions, full HP. That's the difference between "restart the floor" and "respawn at a checkpoint": this is a full floor restart from a saved state, with the window, weapons and MiniLibX left untouched.

Floor progression — reload in place

Winning a floor advances you to the next. The clever bit: it never recreates the window or reloads MiniLibX. advance_floor_after_cutscene() tears down only the floor's heap (grid, doors, sprites, textures), parses the next map, and re-runs the per-floor init chain.

CODE — floor_switch_bonus.c:76 
void	advance_floor_after_cutscene(t_cub *cub)
{
	path = next_floor_map(cub->floor);
	if (!path)
		return ;
	free_textures(cub);
	free_anim_sprites(cub);
	reset_map_state(cub);
	parse_file(cub, path);
	reinit_floor(cub);
}
PLAIN ENGLISH

Load the next floor in place.

Which map is next? (floor 1→2, 2→3, else none)

No next floor? we're done.

Free this floor's wall/floor textures...

...and its animated sprite frames...

...and its grid/doors/sprites heap.

Parse the next .cub (it sets the new FLOOR number).

Rebuild doors, sprites, spawn snapshot, textures, anims.

💡
Floor 1 skips the cutscene; floor 2 doesn't

advance_floor() branches: from floor 2 it plays the ending cutscene first (CUT_END_F2 with action CUT_ACT_NEXT), and the cutscene's finish handler calls advance_floor_after_cutscene. From floor 1 it loads floor 2 directly. Floor 3 never reaches advance_floor at all — its ending is driven from the money pickup.

Cutscenes — a frozen full-screen movie

A cutscene is a lazily-loaded XPM frame sequence. While GS_CUTSCENE is active the world stops updating and render_frame blits only the current frame, full-screen. update_cutscene() picks the frame purely from elapsed time, and when it runs past the last frame, finish_cutscene() decides what happens next based on the action it was started with.

CODE — cutscene_draw_bonus.c:7 
static void	finish_cutscene(t_cub *cub)
{
	action = cub->cutscene.next_action;
	free_cutscene(cub);
	ft_bzero(cub->keys, sizeof(cub->keys));
	if (action == CUT_ACT_NEXT)
		advance_floor_after_cutscene(cub);
	else if (action == CUT_ACT_FINAL)
	{
		cub->cutscene.final_done = 1;
		enter_state(cub, GS_WIN);
	}
	else
		cub->game_state = GS_PLAYING;
}
PLAIN ENGLISH

The cutscene just played its last frame.

Remember what it was told to do next.

Free the frames and clear held keys.

"NEXT" → load the next floor now.

"FINAL" (floor-3 ending) →

...mark the game finished forever...

...and show the win screen (which now loops game-over art).

Plain "PLAY" (the floor-1 intro) → just start playing.

🎬
The three cutscene hooks

CUT_BEGIN_F1 launches the run (action PLAY → gameplay). CUT_END_F2 bridges floor 2 → 3 (action NEXT → reload). CUT_END_F3 is the finale (action FINAL → final_done = 1, terminal GS_WIN). Once final_done is set, draw_endgame loops the gameover_ui frames and update_endgame refuses to advance — the game is over, on purpose.
