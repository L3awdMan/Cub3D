Module 10 · Enemy AI

See the player, walk toward the player, shoot the player — on a cooldown.

The AI is deliberately simple, and that's a strength — it's easy to defend and easy to reason about. Once per frame, every enemy runs one tick: end any finished firing pose, take a step toward you if it can see you, and open fire if you're in range and its cooldown has elapsed. No pathfinding graph, no behaviour trees — just line of sight, distance checks, and a couple of timers.

The driver — one tick per enemy per frame

update_enemies() grabs the wall-clock once and ticks every sprite. The real logic is enemy_tick(), and reading it top to bottom is the AI spec.

CODE — enemy_ai_bonus.c:83 
static void	enemy_tick(t_cub *cub, t_sprite *s, long now)
{
	double	dx;
	double	dy;

	if (s->type >= SP_PICKUP || s->state == SP_DYING)
		return ;
	if (s->state == SP_ATTACKING && now - s->death_ms >= FIRE_MS)
		s->state = SP_ALIVE;
	move_enemy(cub, s);
	dx = cub->player.pos_x - s->x;
	dy = cub->player.pos_y - s->y;
	if (dx * dx + dy * dy > ATTACK_RANGE * ATTACK_RANGE)
		return ;
	if (now < s->next_attack_ms || !los_clear(cub, s))
		return ;
	s->state = SP_ATTACKING;
	s->death_ms = now;
	s->next_attack_ms = now + ATTACK_CD_MS;
	enemy_fire(cub, s);
}
PLAIN ENGLISH

Step one enemy for this frame.

Pickups and corpses don't think. Bail.

If it was firing and FIRE_MS has elapsed...

...drop back to the walk state.

Try to walk toward the player (see below).

Vector to the player.

Out of ATTACK_RANGE? (squared, no sqrt) → done.

Still on cooldown, OR no clear shot? → done.

Otherwise: enter the firing pose...

...stamp when it started (drives the firing anim)...

...arm the cooldown for the next shot...

...and actually fire.

💡
death_ms is reused for the firing timer

One field, two jobs. When an enemy dies, death_ms times the death animation. When it fires, the same field times the firing pose (now - death_ms >= FIRE_MS ends it). They never overlap — a dying enemy can't fire — so reusing the field is safe and saves a struct member.

Line of sight — a thin marched ray

An enemy shouldn't shoot you through a wall. los_clear() answers "can this enemy see the player?" by walking a point from the enemy toward you in steps of 0.1 cell, asking is_blocked() at each step. The first wall (or closed door, or off-grid) returns 0 — no shot. Reach the player with nothing in the way and it returns 1.

CODE — enemy_ai_bonus.c:39 
int	los_clear(t_cub *cub, t_sprite *s)
{
	dx = cub->player.pos_x - s->x;
	dy = cub->player.pos_y - s->y;
	dist = sqrt(dx * dx + dy * dy);
	if (dist < 1e-6)
		return (1);
	t = 0.1;
	while (t < dist)
	{
		if (is_blocked(cub, s->x + dx * (t / dist), s->y + dy * (t / dist)))
			return (0);
		t += 0.1;
	}
	return (1);
}
PLAIN ENGLISH

Can this enemy see the player?

Vector enemy → player.

Straight-line distance.

Practically on top of the player? trivially visible.

March outward from the enemy...

...up to (but not past) the player...

...and if any 0.1-cell sample lands in a wall/door...

...the view is blocked.

Step forward 0.1 cells.

Reached the player with nothing in the way → clear.

⚡
Doors block sight even while they're animating

is_blocked() treats any 'D' cell as solid for line of sight — regardless of how open it is. So an enemy can't snipe you through a half-open door. (The same 'D' check appears in the enemy collision test, which is why enemies never walk through doors either — they can't open them.)

Chasing — move per axis, slide on walls

move_enemy() walks an alive enemy toward you, but only inside a band: closer than CHASE_RANGE (8 cells) and farther than ENEMY_STOP_DIST (1 cell), and only with clear sight. The boss (SP_FLUID) is exempt — it holds its ground. The direction is normalised and scaled by ENEMY_SPD (0.02 cells/frame, deliberately slower than your MOVE_SPD).

CODE — enemy_move_bonus.c:53 
static void	slide_toward(t_cub *cub, t_sprite *s, double vx, double vy)
{
	nx = s->x + vx;
	ny = s->y + vy;
	if (!enemy_blocked(cub, nx, s->y))
		s->x = nx;
	if (!enemy_blocked(cub, s->x, ny))
		s->y = ny;
}
PLAIN ENGLISH

Move along (vx, vy), one axis at a time.

Proposed new X and Y.

Is the X move alone clear? then take it.

Is the Y move alone clear (from the possibly-updated X)? take it.

Blocking one axis still lets the other slide → no clipping.

Testing each axis independently is exactly the player's collision trick from Module 3, reused. enemy_blocked() checks the four corners of an ENEMY_PAD (0.3) box, so the body has width and an enemy slides along a wall instead of jamming into it.

📝
A corrector's gotcha: the stale comment

The header comment in enemy_ai_bonus.c still says "Enemies do not move (chase is a future phase)." That comment is out of date — enemy_tick calls move_enemy, and enemies do chase. If a corrector quotes the comment, point them at the actual call. The code is the source of truth.

The tunables

ATTACK_RANGE 6.0Cells within which a seeing enemy can hit you.
CHASE_RANGE 8.0Cells within which a seeing enemy starts walking in.
ENEMY_STOP_DIST 1.0Stops closing once this near, so it keeps shooting distance.
ENEMY_SPD 0.02Cells per frame — slower than the player.
ATTACK_CD_MS 900Cooldown between an enemy's shots.
FIRE_MS 270How long the firing pose plays before snapping back to alive.
ENEMY_PAD 0.3Half-width of the enemy collision box.
