Module 2 · Raycasting math

One beam, one grid, one wall stripe.

Think of the map as graph paper. You're a dot on it, looking in some direction. For each column on the screen, the renderer fires a beam from your dot, walks it cell-by-cell across the graph paper until it bumps into a wall cell, and asks: "how far did you go?" That distance becomes the height of a vertical stripe on the screen. Do that 1280 times and you have a frame.

The cast of characters in t_ray

Each beam carries its own little notebook of variables as it walks the grid. Before we touch the math, learn the words.

🎯

dir_x, dir_y

Where the beam is pointing. A unit-ish vector built from the player's facing + a sideways shove for this particular column.

📍

map_x, map_y

The integer grid cell the beam is currently sitting in. Bumped by ±1 each DDA step.

📏

delta_x, delta_y

How far the beam travels to cross one full cell on the X axis (or Y axis). Constant for the whole trip.

📐

side_dist_x, side_dist_y

Distance from the player to the next vertical grid line (or next horizontal grid line). Updated every step.

🧭

step_x, step_y

+1 or −1 per axis. Tells the DDA which direction to step the cell index in.

🪞

side

0 if the last hop crossed a vertical grid line, 1 if it crossed a horizontal one. Decides which texture face was hit.

Step 1 — Aim the beam (init_ray)

The screen column you're rendering (left edge, middle, right edge) decides how much the beam tilts off your forward direction. The player has two vectors: dir (forward) and plane (a perpendicular sideways vector whose length defines the FOV). The beam direction for column x is simply dir + plane × camera_x, where camera_x remaps the column to the range −1 → +1.

CODE — ray_utils.c:22 
void	init_ray(t_ray *ray, t_player *p, int x)
{
	double	camera_x;

	camera_x = 2.0 * x / WIN_W - 1.0;
	ray->dir_x = p->dir_x + p->plane_x * camera_x;
	ray->dir_y = p->dir_y + p->plane_y * camera_x;
	ray->map_x = (int)p->pos_x;
	ray->map_y = (int)p->pos_y;
	if (ray->dir_x == 0)
		ray->delta_x = 1e30;
	else
		ray->delta_x = fabs(1.0 / ray->dir_x);
	if (ray->dir_y == 0)
		ray->delta_y = 1e30;
	else
		ray->delta_y = fabs(1.0 / ray->dir_y);
}
PLAIN ENGLISH

For screen column x, build the beam.

First a scratch number.

Map column 0 → −1, middle column → 0, last column → +1.

Beam direction = forward vector + sideways plane vector × that scalar.

Same for the Y component — together they form the beam direction.

Remember which grid cell the player is currently sitting in.

Both coordinates of the player's cell.

If the beam has no X component, set delta to a huge sentinel.

(prevents division by zero in the next step)

Otherwise delta_x = how far the beam moves total per 1 unit of X. That's |1 / dir_x|.

Same sentinel guard for Y.

Same formula: delta_y = how far the beam moves per 1 unit of Y.

📐
Why |1 / dir_x|?

If the beam moves dir_x units along X for every 1 unit of beam-length, then it needs 1 / dir_x units of beam-length to advance by 1 unit of X. That's exactly how far we have to travel to cross from one vertical grid line to the next. Absolute value because we only care about distance, not direction.

Step 2 — Distance to the first wall (init_step_side)

Your player is somewhere inside a cell, not on a grid line. side_dist_x is "how far the beam has to travel before it crosses the very next vertical grid line." Symmetric story for side_dist_y. The math depends on whether the beam is pointing left or right (and up or down).

CODE — ray_utils.c:48 
if (ray->dir_x < 0)
{
	ray->step_x = -1;
	ray->side_dist_x = (p->pos_x - ray->map_x) * ray->delta_x;
}
else
{
	ray->step_x = 1;
	ray->side_dist_x = (ray->map_x + 1.0 - p->pos_x) * ray->delta_x;
}
PLAIN ENGLISH

Beam is pointing left.

Each grid step shrinks map_x by 1.

Distance to the next vertical line = how far you are past the left edge of the cell, scaled by the per-unit cost.

Otherwise it's pointing right.

Each grid step grows map_x by 1.

Distance to the next vertical line = how far you are before the right edge of the cell, scaled.

Step 3 — Walk until you hit something (the DDA loop)

DDA is one of those algorithms that sounds intimidating and turns out to be five lines. The whole idea: at every step, look at side_dist_x vs side_dist_y. Whichever is smaller is the nearer grid line. Cross it (bump the cell index, add the delta to that side_dist), and ask: did I land on a wall?

CODE — raycaster.c:19 
static void	advance_ray(t_ray *ray)
{
	if (ray->side_dist_x < ray->side_dist_y)
	{
		ray->side_dist_x += ray->delta_x;
		ray->map_x += ray->step_x;
		ray->side = 0;
	}
	else
	{
		ray->side_dist_y += ray->delta_y;
		ray->map_y += ray->step_y;
		ray->side = 1;
	}
}
PLAIN ENGLISH

Take one step of the DDA.

The next vertical grid line is closer than the next horizontal one.

Pay the cost: distance grows by one full cell-width worth of X-axis travel.

Bump the X cell index by +1 or −1.

Mark that we crossed an East/West face.

Otherwise the next horizontal grid line is closer.

Same idea on the Y axis.

Bump the Y cell index.

Mark that we crossed a North/South face.

The DDA loop and its stop condition

The loop just keeps calling advance_ray and asking "did I land on a wall yet?" Walls ('1') always stop it. Doors ('D') call a special function we'll meet in Module 5. Open space ('0') keeps the loop going.

CODE — raycaster.c:45 
static int	dda_step(t_cub *cub, t_ray *ray)
{
	t_map	*map;
	char	c;
	double	hit;

	map = &cub->map;
	advance_ray(ray);
	if (ray->map_y < 0 || ray->map_y >= map->height || ray->map_x < 0
		|| ray->map_x >= (int)ft_strlen(map->grid[ray->map_y]))
		return (1);
	c = map->grid[ray->map_y][ray->map_x];
	if (c == '1')
		return (1);
	if (c == 'D')
	{
		hit = ray_hit_fraction(ray, &cub->player);
		if (door_allows_passage(cub, ray->map_y, ray->map_x, hit))
			return (0);
		ray->door = 1;
		ray->door_hit = hit;
		return (1);
	}
	return (0);
}

Solid wall → stop.

Step 4 — Real distance, no fisheye (calc_draw_params)

The naive "Euclidean distance from player to hit point" produces a curved fisheye image — corners stretch outward. The fix is to use only the perpendicular component of the hit distance, measured along the player's forward direction. That's side_dist − delta on the axis that was crossed last. From there, screen height is just WIN_H / perp_dist: closer wall → bigger stripe.

CODE — ray_utils.c:84 
if (ray->side == 0)
	ray->perp_dist = ray->side_dist_x - ray->delta_x;
else
	ray->perp_dist = ray->side_dist_y - ray->delta_y;
if (ray->perp_dist < 0.001)
	ray->perp_dist = 0.001;
dw->height = (int)(WIN_H / ray->perp_dist);
dw->start = horizon - dw->height / 2;
...
dw->end = horizon + dw->height / 2;
PLAIN ENGLISH

Crossed a vertical grid line — perpendicular distance is along X.

Subtract one delta back off because we already over-stepped into the wall.

Crossed a horizontal grid line.

Same correction on Y.

Guard against divide-by-zero in the height math below.

Stripe height in pixels: closer = taller, classic inverse-distance projection.

Center the stripe vertically around the horizon.

End at horizon + half-height.

🐟
Why perpendicular distance fixes fisheye

If you used Euclidean distance, rays at the edge of your view would be longer than rays in the center even for the same flat wall — that's a bowed image. By measuring only the component along your forward axis, every column of a flat wall reports the same depth, and the wall renders flat.

Step 5 — Where on the texture did we hit? (calc_wall_x)

Now we know which face of which wall got hit. We still need to know where on that face — left edge of the brick? right edge? — so we can pick the matching texture column. That's the fractional part of the hit position along whichever axis the beam was sliding along.

CODE — draw_wall.c:24 
double	calc_wall_x(t_ray *ray, t_player *p)
{
	double	wall_x;

	if (ray->side == 0)
		wall_x = p->pos_y + ray->perp_dist * ray->dir_y;
	else
		wall_x = p->pos_x + ray->perp_dist * ray->dir_x;
	wall_x -= floor(wall_x);
	return (wall_x);
}
PLAIN ENGLISH

For ray + player, return the hit position across the wall face (0..1).

If we hit a vertical wall face, slide along the Y axis to find the hit point.

Player Y + how far the beam traveled × the beam's Y component.

If we hit a horizontal face, slide along X instead.

Symmetric formula.

Drop the integer part — we only want the fraction inside this 1×1 cell face.

Return that fraction. The texture sampler turns it into a column index.

There's a sister helper for doors

ray_hit_fraction does the same idea as calc_wall_x, but it runs inside the DDA — before perp_dist is even finalized. The door pass-through test needs the hit fraction the moment the beam enters a 'D' cell, so this helper uses side_dist − delta directly to compute the entry distance instead of trusting perp_dist.

🔁
Why two near-identical helpers?

It looks like duplication but it's an ordering constraint. calc_wall_x runs once per column after the DDA finishes, when perp_dist is set. ray_hit_fraction has to run during the DDA, mid-walk, on every door cell. Same math, different lifecycle. Keeping them separate lets the door code stay decoupled from wall-drawing.
