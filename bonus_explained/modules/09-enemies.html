Module 9 · Enemies & the bestiary

A character in the map text becomes a living, animated monster.

The sprite engine from the last module can draw a card in the world. Now we fill the world with things to shoot. Enemies are born straight out of the .cub map: a single character like 2 or 3 spawns a robot or a boss. This module covers how tiles turn into entities, the tiny state machine each one runs, and how the Blake Stone bestiary swaps art per floor.

One char → one role

tile_type() is the dictionary. It maps a map character to a sprite type index, returning -1 for anything that isn't a sprite tile. Five enemy roles, plus the weapon pickups (which map to SP_PICKUP + i).

'2' → SP_POD The standard guard/robot of the floor.
'3' → SP_FLUID The boss. The only enemy with more than 1 HP.
'A' → SP_SCIENTIST Scientist enemy.
'F' → SP_SPECIAL The fluid alien — shared on every floor, no firing set.
'B' → SP_POD_ALIEN The pod alien.
"789P" → SP_PICKUP + i Weapon pickups (PICKUP_CHARS), one frame each.

Spawning: count, allocate, fill

init_sprites() runs in two passes. First count_sprites() walks the grid and counts sprite tiles so we know how big the array must be. Then it allocates — and here's a detail correctors love — it over-allocates to double the count (sprite_cap = sprite_count * 2). That spare room is for runtime drops: every enemy you kill can append one meat/money reward without a realloc.

CODE — sprites_bonus.c:100 
void	init_sprites(t_cub *cub)
{
	cub->sprite_count = count_sprites(cub);
	if (cub->sprite_count <= 0)
		return ;
	cub->sprite_cap = cub->sprite_count * 2;
	cub->sprites = ft_calloc(cub->sprite_cap, sizeof(t_sprite));
	if (!cub->sprites)
		exit_error(cub, "Memory allocation failed");
	fill_sprites(cub);
}

💡
Why erase enemies but keep pickups in the grid?

Enemies move and collide via the sprite system, so the raycaster must never treat their cell as a wall — erase it. Weapon pickups are different: weapon_pickup() reads the original tile character (7/8/9/P) off the grid to know which weapon you stepped on, and clears it itself on pickup. So pickups stay as their letter; enemies become '0'.

⚡
The boss HP one-liner

hp = 1 + (t == SP_FLUID) * (BOSS_HP - 1) is a branchless trick. For any normal enemy (t == SP_FLUID) is 0, so HP = 1. For the boss it's 1, so HP = 1 + (8 - 1) = 8. One line, no if.

The state machine

Each t_sprite carries a state that's just three values. The renderer (module 8) reads state to pick the animation; the AI (next module) writes it. That's the whole contract.

0
SP_ALIVE

Loops the walk animation forever and is free to chase. Default state at spawn.

2
SP_ATTACKING

Set by the AI when it fires. Plays the firing pose for FIRE_MS, then the AI flips it back to alive.

1
SP_DYING

Set by shoot_hitscan() when HP hits 0. Plays the death set once and freezes on the last frame — a permanent corpse.

Per-floor art — the t_floorset matrix

Roles are floor-agnostic (a "pod" is role 0 on every floor), but the art changes. floor_set(cub->floor) returns a table of four NULL-terminated path lists per role — walk, fire, death, and projectile — and load_anim_sprites() loads each into the matching slot (role, firing_type(role), death_type(role), proj_type(role)).

💡
The fluid alien is the odd one out

Role 3 (SP_SPECIAL) has no firing art — in the floor tables its "fire" list is literally g_special_walk (the walk loop reused) and its projectile list is g_no_proj (empty). An enemy with an empty projectile list attacks invisibly with instant damage instead of launching a shot. Keep that in mind for the combat module.

Loading each frame is plain MiniLibX: load_one_frame() calls mlx_xpm_file_to_image and then records the transparent colour by sampling the very first pixel — a->transp[i] = *(unsigned int *)t->data. That's the (0,0) "None" pixel every Blake Stone sprite atlas puts in its border, and it's exactly what the column blitter skips.
