Module 12 · HUD & feedback

Everything the player reads without thinking: bars, a counter, and two coloured flashes.

The HUD is drawn last, straight onto the finished image buffer, so it always sits on top of the 3D world. None of it is clever 3D — it's rectangles, a pre-rendered panel, and a couple of full-screen tints. But the layering order and the data each piece reads matter, and that's exactly what a corrector will poke at. (The circular minimap has its own module — Module 6.)

Health bars — fill a box, colour by ratio

draw_health_bars() always draws the player bar (bottom-left, 260×24 px) and then conditionally the boss bar. The drawing primitive draw_hud_bar() is dead simple: paint a dark background box, then paint a coloured fill box whose width is box_width × ratio.

CODE — hud_bar_draw_bonus.c:42 
void	draw_hud_bar(t_cub *cub, int box[4], double ratio, int boss)
{
	if (ratio < 0)
		ratio = 0;
	if (ratio > 1)
		ratio = 1;
	fill_rect(cub, box, 0x171820);
	size[0] = (int)(box[2] * ratio);
	size[1] = box[3];
	set_box(fill, box[0], box[1], size);
	fill_rect(cub, fill, bar_color(ratio, boss));
}

Draw one bar: box = [x, y, w, h], ratio = fill fraction.

Clamp ratio into [0, 1]...

Paint the dark empty track first.

Fill width = full width × ratio.

Same height as the track.

Paint it in the ratio-dependent colour (green/yellow/red).

💡
The boss bar only appears when it should

draw_boss_bar() has two gates: the player must be standing in a boss cell (player_in_boss_room() checks the grid char is 'Z'), and a live SP_FLUID boss must still exist in the sprite list. Its ratio is boss.hp / BOSS_HP, so it drains one chunk per shot you land. No boss, or you've left the room → no bar.

The "enemies remaining" counter

This is a neat reuse of art: 24 pre-rendered panel frames (lives_0 … lives_23) sit in the black slot of the floor HUD. The drawer just blits the frame indexed by cub->lives. The count is seeded from the floor's killable enemies and ticks down on each kill (you saw cub->lives-- in shoot_hitscan).

CODE — lives_hud_bonus.c:36 
int	count_enemies(t_cub *cub)
{
	n = 0;
	i = -1;
	while (++i < cub->sprite_count)
		if (cub->sprites[i].type < SP_PICKUP)
			n++;
	if (n > LIVES_MAX)
		n = LIVES_MAX;
	return (n);
}

How many killable enemies are on this floor?

...so pickups and rewards don't inflate it.

...(there are only lives_0..lives_23).

⚡
Why type < SP_PICKUP is the "is it an enemy?" test

Remember the type ordering contract from Module 8: roles 0–4 are the only alive enemies, and everything from SP_PICKUP (5) upward is loot or projectile art. So a single comparison cleanly separates "things that count as lives" from "things that don't". The cap at LIVES_MAX guarantees the index never runs off the 24-frame array.

The floor HUD panel itself (floor_hud) is one XPM per floor, blitted across the top of the screen and scaled to WIN_W. The lives counter draws into a black slot inside it, and the boss bar is positioned just below it (hud_bottom_y() measures the panel's scaled height). The crosshair is the 9-pixel cross from shade.c (Module 7), drawn dead last so nothing covers the reticle.

The two flashes — post-process vignettes

Both flashes run after the whole frame is drawn, tinting cub->img directly. They're full-screen pixel scans, but they only run during the brief fade — when no flash is active the function returns immediately, so there's no cost in normal play.

🩸

Damage flash

Reddens the screen, strongest at the corners (edge_factor = squared distance from centre). Alpha ramps from HURT_MAX_A to 0 over HURT_FADE_MS since player.hurt_ms.

💚

Pickup flash

Softly adds green (meat) or gold (money) in a FLASH_EDGE_PX border band only. Fades from FLASH_MAX_A over FLASH_FADE_MS since flash_ms.

💡
The flashes are mutually exclusive — newest wins

You can't be red and green at the same time. The damage flash bails if flash_ms > hurt_ms; the pickup flash bails if hurt_ms >= flash_ms. Whichever event happened most recently is the one that draws. A clean way to arbitrate two effects that share the screen without blending into mud.

Reward pickups close the loop

Kills drop loot (Module 11): a normal enemy drops SP_MEAT, the boss drops SP_MONEY. collect_rewards() runs each frame, and when you walk within REWARD_PICK_DIST of one, reward_effect() applies it: meat heals MEAT_HEAL (clamped at full) and flashes green; money flashes gold.

🏆
Grabbing the money bag is the win condition

Look closely at reward_effect: collecting SP_MONEY doesn't just flash gold — on floor 3 it starts the final cutscene (CUT_END_F3), and on any other floor it calls enter_state(cub, GS_WIN). So the whole game loop is: kill the boss → it drops money → you grab it → you win the floor. That hand-off into the game-state machine is the subject of the next module.
