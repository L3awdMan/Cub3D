Module 8 · Sprite engine

Walls are columns. Sprites are flat cards that always face you.

The raycaster only knows how to draw vertical wall stripes. Every enemy, boss, ammo pickup, dropped meat and flying projectile in the bonus is a billboard — a single texture pasted onto the screen, scaled by distance, and clipped so walls hide what's behind them. This module is the engine that turns a world position (x, y) into pixels. Everything in the next four modules (enemies, AI, combat, pickups) rides on top of it.

The three jobs, every frame

draw_sprites() runs after the wall pass, because it needs cub->zbuf — the per-column wall depth the raycaster just filled in. Each frame it does exactly three things, in order.

1
Sort far-to-near

sort_sprites() orders the array so distant sprites are drawn first and near ones paint last, on top. Classic painter's algorithm.

2
Transform to camera space

sprite_transform() projects each world position into a screen column + depth + on-screen rectangle, using the inverse of the camera matrix.

3
Blit column by column

draw_sprite_cols() walks the rectangle, drops any column the wall is in front of (z-test), and copies texels for the rest.

CODE — sprite_draw_bonus.c:104 
void	draw_sprites(t_cub *cub)
{
	int	i;
	t_spr	s;

	if (!cub->sprites || cub->sprite_count <= 0)
		return ;
	sort_sprites(cub);
	i = 0;
	while (i < cub->sprite_count)
	{
		if (expire_dead_boss(cub, i))
			continue ;
		sprite_transform(cub, &cub->sprites[i], &s);
		if (s.depth >= SP_NEAR)
			draw_sprite_cols(cub, &s);
		i++;
	}
}
PLAIN ENGLISH

For each frame, draw every sprite.

i = loop index. s = the screen-space draw params for one sprite.

Nothing to draw? bail.

Order them far → near so the painter's algorithm works.

Walk every sprite.

Dead boss past its timer? remove it + drop money, re-check this slot.

Turn world (x,y) into screen rectangle + depth.

In front of the camera (not behind / not on top of us)?

Then blit its columns.

The maths bit — sprite_transform

This is the one piece of real linear algebra in the whole sprite system, and it's worth getting. The camera is described by two vectors: dir (where you're looking) and plane (the camera plane, perpendicular to dir, that sets the field of view). Together they form a 2×2 matrix that maps camera space → world space. To draw a sprite we need the opposite: world → camera. So we invert the matrix.

CODE — sprite_draw_bonus.c:72 
	rx = sp->x - p->pos_x;
	ry = sp->y - p->pos_y;
	inv = p->plane_x * p->dir_y - p->dir_x * p->plane_y;
	if (inv > -1e-9 && inv < 1e-9)
	{
		s->depth = 0.0;
		return ;
	}
	inv = 1.0 / inv;
	tx = inv * (p->dir_y * rx - p->dir_x * ry);
	s->depth = inv * (-p->plane_y * rx + p->plane_x * ry);
	if (s->depth < SP_NEAR)
		return ;
	s->screen_x = (int)((WIN_W / 2.0) * (1.0 + tx / s->depth));
	s->shade = FOG_K / (FOG_K + s->depth);
	s->tex = current_frame(cub, sp, &s->transp);
	sprite_rect(cub, sp, s, (int)fabs(WIN_H / s->depth));
PLAIN ENGLISH

(rx, ry) = sprite position relative to the player.

inv = determinant of the camera matrix.

If it's ~0 the matrix is singular (degenerate)...

...so mark depth 0 and skip — never divide by it.

Otherwise flip it to 1/det once, reuse below.

tx = horizontal camera coordinate of the sprite.

depth = how far in front of the camera plane it sits.

Behind us or right on the lens? skip.

Centre column + horizontal offset, scaled by depth → screen X.

Fog: near = bright (→1), far = dark (→0).

Pick the animation frame for this state (alive/dying/firing).

Full-cell on-screen size at this depth = |WIN_H / depth|.

⚡
Why depth is the perpendicular distance, not the straight-line distance

Exactly like walls, the sprite's height comes from its distance along the camera direction, not the raw Euclidean distance. Using the perpendicular distance is what keeps sprites the same size whether they're dead-centre or near the edge of your view — no fish-eye bulge. It's the plane/dir projection that gives you that for free.

From depth to a rectangle — sprite_rect

The full billboard height at a given depth is |WIN_H / depth| (same formula as a wall stripe). A square card centred on screen_x gives the left/right bounds. The clever part is the vertical anchor: pickups don't fill the column — they get shrunk to PICKUP_SCALE (0.40) but keep the same floor line sy1 as a full-size alien, so ammo and meat rest on the ground instead of floating at eye level.

CODE — sprite_col_bonus.c:16 
void	sprite_rect(t_cub *cub, t_sprite *sp, t_spr *s, int full)
{
	if (sp->type >= SP_PICKUP)
		s->size = (int)(full * PICKUP_SCALE);
	else
		s->size = full;
	s->sx0 = s->screen_x - s->size / 2;
	s->sx1 = s->screen_x + s->size / 2;
	s->sy1 = cub->horizon + full / 2;
	s->sy0 = s->sy1 - s->size;
}
PLAIN ENGLISH

Build the on-screen box. `full` = full-cell size at this depth.

Is this a pickup (ammo/meat/money), not an alien?

Then shrink it to 40% so it sits small on the floor.

Aliens get the full height.

Left edge = centre − half width.

Right edge = centre + half width.

Bottom = the floor line of a FULL cell (shared by all sprites).

Top = bottom − actual size (small pickups start lower down).

💡
sy1 uses full / 2, but sy0 uses size

Read those last two lines again. The bottom always lands on the full-cell floor line, but the top is measured up by the real size. That asymmetry is the whole "things sit on the ground" trick — shrink a sprite and it shrinks downward toward its feet, not toward its centre.

The z-buffer — why walls hide sprites

The raycaster left a wall depth for every screen column in cub->zbuf[x]. A sprite column is only drawn if the sprite is nearer than the wall in that exact column: s->depth < cub->zbuf[x]. That single comparison is the entire occlusion system — an enemy behind a pillar is silently cut off column by column, and you never see it bleed through.

CODE — sprite_col_bonus.c:57 
void	draw_sprite_cols(t_cub *cub, t_spr *s)
{
	int	x;

	if (s->size <= 0 || !s->tex)
		return ;
	x = s->sx0;
	while (x < s->sx1)
	{
		if (x >= 0 && x < WIN_W && s->depth < cub->zbuf[x])
			draw_sprite_strip(cub, s, x);
		x++;
	}
}
PLAIN ENGLISH

Draw all visible columns of one transformed sprite.

No size or no texture? nothing to do.

Start at the sprite's left edge.

Walk to the right edge.

On screen AND nearer than the wall in this column?

Draw this vertical strip; otherwise skip (wall wins).

Inside draw_sprite_strip(), each screen row is mapped back to a texel with nearest-neighbour sampling (tx = (x - sx0) * tex->width / size), the recorded transparent colour s->transp is skipped (that's how the alien's outline stays see-through), and every surviving texel is dimmed by shade_rgb(color, s->shade) so distant sprites fog out the same way walls do.

Where each sprite type lives

Sprite "type" is just an index into cub->sprite_anims[], and the ordering is a contract shared across the whole bonus. Get this and you understand how one array feeds enemies, corpses, attacks, projectiles and loot.

SP_POD … SP_POD_ALIEN (0–4) The five alive enemy roles. These also double as the walk-loop animation slot.
SP_PICKUP (5–8) Weapon pickups. SP_PICKUP + i is the i-th PICKUP_CHARS weapon, drawn grounded.
death_type(t) = 9 + t Play-once corpse animation for role t (slots 9–13).
firing_type(t) = 14 + t Attack/firing pose set for role t (slots 14–18).
proj_type(t) = 19 + t Flying projectile art for role t (slots 19–23).
SP_MEAT 24 · SP_MONEY 25 Reward drops. SP_TYPES = 26 total slots.

The animation clock — current_frame

One function picks which frame to show, branching on the sprite's state. There's no per-sprite timer stored — it all reads off the shared wall clock now_ms(), which keeps every walking alien in sync for free.

🚶
SP_ALIVE → walk loop

idx = (now_ms() / ANIM_MS) % count. Loops forever at 150 ms/frame.

💀
SP_DYING → death set, once

idx = (now_ms() − death_ms) / DEATH_MS, clamped to the last frame. The corpse stays drawn on its final frame.

🔫
SP_ATTACKING → firing set

Same DEATH_MS cadence but % count so it cycles while the enemy is mid-attack, then the AI snaps it back to alive.
